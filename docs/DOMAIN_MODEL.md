# Domain model — initial entities

All IDs are UUIDs. Timestamps are UTC. Distances are stored in metres; durations in seconds; money in integer minor units with ISO currency code.

- **User**: id, phone, display_name, status, created_at
- **DriverProfile**: user_id, verification_status, rating_summary
- **Vehicle**: id, driver_id, make, model, color, plate_number, seat_capacity, status
- **PassengerRequest**: id, passenger_id, origin, destination, route_geometry, route_distance_m, offered_rate_minor_per_km, estimated_fare_minor, departure_window, status, expires_at
- **DriverTrip**: id, driver_id, vehicle_id, origin, destination, route_geometry, direct_distance_m, departure_window, status
- **TripOffer**: id, driver_trip_id, ordered_stops, passenger_request_ids, vehicle_distance_m, passenger_revenue_minor, platform_fee_minor, driver_net_minor, status, expires_at
- **Booking**: id, trip_offer_id, passenger_request_id, passenger_id, seat_count, fare_minor, status, accepted_at, cancelled_at
- **LedgerAccount**: id, owner_type, owner_id, currency
- **LedgerEntry**: id, account_id, transaction_id, direction, amount_minor, entry_type, reference_type, reference_id, created_at
- **Payment**: id, user_id, provider, provider_reference, amount_minor, currency, status, idempotency_key
- **TripEvent**: id, driver_trip_id, actor_id, event_type, payload, created_at

## Important distinctions

Passenger route distance is not the same as the driver's vehicle distance. The driver's vehicle distance includes travel to pickups, between stops and to drop-offs. Passenger fare is calculated independently for each passenger's own route and offered rate.

## State machines (first draft)

PassengerRequest: draft → searching → matched → in_trip → completed; searching/matched may transition to cancelled or expired.

DriverTrip: draft → published → in_progress → completed; published may transition to cancelled.

Booking: pending → confirmed → picked_up → completed; confirmed may transition to cancelled. Cancellation fees/refunds depend on a separately approved policy.

These transitions must be enforced server-side; clients may request transitions but cannot set arbitrary statuses.

## Additional fields and states for live dispatch

- PassengerRequest discovery fields: `searching_started_at`, `matched_at`, `search_expires_at`; geometry remains the road-route LineString. Searching requests are queryable by status and indexed spatially.
- TripOffer/Booking provisional confirmation fields: `confirmed_at`, `free_cancel_until`, `provisional_status` (or equivalent explicit state). The 10-second deadline is generated by the server.
- Booking lifecycle is refined to: `pending → provisional_confirmed → confirmed → picked_up → completed`; `provisional_confirmed` may transition to `cancelled` without fee before `free_cancel_until`.
- PassengerRequest: `searching → provisional_matched → matched → in_trip → completed`; `searching` can be cancelled/expired; `provisional_matched` can be cancelled during the free window or returned to searching if the driver withdraws.
- Driver matching preferences: mode (`flexible` or `destination`), pickup road-distance limit, optional target destination, and target-destination tolerance in road metres.
- Passenger discovery preferences: origin-to-origin road-distance limit and destination-to-destination road-distance limit. These are filters only; they do not reserve requests.
- A passenger's free-cancellation deadline is stored per booking, not inferred from a client timer. Multi-passenger offers may need recomputation if one passenger cancels.



## Live map overlays and candidate combination identity

- A passenger request is one canonical record with one stable ID and one lifecycle state. It is never copied just because it participates in multiple candidate combinations.
- A **CandidateCombination** is a driver-specific, derived result/snapshot containing an ordered stop sequence, the set of passenger request IDs, full vehicle route geometry/distance, total passenger revenue, revenue per vehicle kilometre, feasibility details and rank within that driver's current result set.
- Candidate combinations may overlap: the same passenger request ID can be referenced by multiple candidate combinations, including combinations belonging to different drivers. A request therefore has no single global rank or map color.
- Map colors are computed per driver's ranked result set at presentation time: rank 1 red, rank 2 green, rank 3 blue. Driver-published searching routes and passenger searching requests use their separate passenger-map conventions (black and red respectively). Do not persist these display colors as domain state.
- A **ProvisionalClaim** (or equivalent transactional claim on request IDs) prevents any request in an accepted provisional combination from being offered to another driver. The claim must be globally visible to matching queries immediately after the accepting transaction commits.
- On provisional acceptance, atomically lock/claim every included passenger request, create the provisional bookings, and invalidate/recompute every other candidate combination that references any claimed request. Enforce this with database transactions and appropriate row/advisory locks or uniqueness constraints; a stale client-side list cannot authorize acceptance.
- Preserve a short-lived presentation snapshot for the accepting driver's 10-second blink animation, including the combination ID and the rank/color it had at confirmation. This is historical UI metadata only; it must not make the claimed requests eligible again. Other drivers' views must remove the claimed requests from available results immediately.
- The passenger and driver Map/List views are projections of the same server-side result/state. View switching must not alter filters, matching state, or selected entity. Realtime events invalidate or refresh both projections.
- If a passenger cancels during the free window, recompute the provisional combination from the remaining canonical request IDs. Commit the revised stop sequence and claims atomically, or release/cancel the affected provisional offer and restore only still-eligible requests to searching.
